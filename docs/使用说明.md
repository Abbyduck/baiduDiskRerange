# 工作流程与工具入口

## 推荐顺序

1. 保存完整盘点及当前状态，复用已有索引，避免为每份报告重复遍历。
2. 确认分类容器与整包边界。进入完整课程或合集后停止拆分，内部 Week、Level、音视频与讲义保留在同一包里。
3. 阅读逐包简介，核对主题、用途、语种及建议大类。照片按来源文件夹统计。
4. 对完全重复、严格包含和版本有差异的整包分别核对；任何操作以当前路径和内容指纹为依据。
5. 大类确认后，再提出整包归位清单，之后细化英文等大类的内部结构。

## 源码分组

| 用途 | 文件 |
| --- | --- |
| 官方 MCP 的本地 stdio 桥接 | `bridge.mjs`、`Start-BaiduMcp.ps1`、`Save-Token.ps1` |
| 可恢复的目录盘点 | `crawl_inventory.py`、`recursive_inventory.py` |
| 数据目录与文件元信息 | `project_paths.py`、`dedup_live_index.py` |
| 整包边界及包含关系 | `package_boundaries.py`、`package_containment.py` |
| 当前整包介绍与清单 | `build_package_catalog.py`、`build_package_review.py` |
| 只读本地页面入口 | `serve_reports.py`、`Start-Reports.ps1`、`package_review_server.py` |
| 已确认操作的服务及核对 | `dedup_review_server.py`、`package_delete_service.py`、`reconcile_dedup.py` |
| 旧批次原位恢复与验证 | `restore_deleted_packages.py` |
| 早期分析及报告重建 | `analyze_inventory.py`、`analyze_folder_duplicates.py`、`build_report.py`、`build_proposal_html.py`、`build_remaining_report.py` |

早期报告构建器保留用于重建分析材料和兼容历史执行记录。当前整包界面来自 `build_package_review.py`，不要用早期按子树识别的清单替代它。

## 重建衍生材料

清理后的原始数据仍在 SQLite 数据库与完整实时索引中。早期的逐文件理解、重复候选和图表统计可以按需重建：

```powershell
python baidu-mcp/analyze_inventory.py
python baidu-mcp/build_report.py
python baidu-mcp/build_proposal_html.py
```

以上会生成早期目录建议及其配套材料。当前的逐包介绍使用实时索引，单独运行 `build_package_catalog.py` 即可，无需重新访问网盘。

`recursive_inventory.py` 是原始完整盘点的游标式补全脚本，实际运行会访问云端并更新本地盘点；已有完整基线时不应为了查看报告再运行它。

## 操作服务

日常查看使用 `Start-Reports.ps1`。需要继续已有整包去重流程时，原服务仍可手动启动：

```powershell
python baidu-mcp/dedup_review_server.py --port 8765
```

同一端口只能运行一个服务。此服务读取已有策略和清单；当前项目只允许经整包边界核对的候选，并在实时核对后要求页面最终确认。清理工作没有放宽任何策略或补发历史请求。

`restore_deleted_packages.py` 专用于本项目已有恢复清单，包含固定范围校验，不能当作通用“一键恢复”命令。`reconcile_dedup.py` 用于只读核实已有操作批次。查看项目和执行测试均不需要运行这两个工具。

## 本机数据的保管

所有私人数据集中在 Git 忽略的 `local-data/`。备份本项目时应另行备份这个目录及本机加密凭据；克隆 GitHub 仓库只能恢复代码。DPAPI 凭据与当前 Windows 账号绑定，换电脑需要重新授权。

原始基线、当前快照、已删除状态及恢复记录存在相互引用。清理缓存前先检查是否被这些记录引用；不能仅凭文件日期判断整份快照已无用。
